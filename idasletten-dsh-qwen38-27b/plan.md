# Idasletten — Table Football Tournament App
 
> **Build conventions**
> - Use the folder name as app name if deploying to Fly.io.
>
 
---
 
## 1. Overview
 
Idasletten is a web app for running table‑football (foosball) tournaments: tracking players, teams, matches, results, and a configurable scoreboard. It has a Norse‑mythology theme.
 
Authentication is optional. Anyone can browse and record match results without logging in. Logging in (via Azure AD) is only required to **create tournaments** and to **edit already‑completed matches**.

## 3. Scoring systems  *(largest open area)*
 
The tournament's `ScoreSystem` determines how `TournamentPlayer.Score` is calculated. The spec lists four systems but does not define their rules. Each needs to be specified:
 
- **Elo** — Use normal ELO scoring mechanism. When the teams consists of multiple players, then take an average score on a team. 
- **TrueSkill** — Use the Moserware.Skills https://github.com/moserware/Skills library to calculate the TrueSkill score. [Samples](https://github.com/moserware/Skills/blob/master/Sample/Content/TrueSkillSamples.cs.pp)
- **Lives** — When a game is lost, then you lose a life. .
- **WinCount** — presumably `Score = WinCount`. Confirm tie‑breakers (goal difference?).

## 4. Pages
 
### `/` — Home
- A large hero image and this text:
  > *"Idasletten (Iðavöllr) findes i nordisk mytologi lige uden for Valhals porte. Det er her vikingerne som er døde i krig udkæmper deres drabelige slag hver dag, som øvelse til Ragnarok. Hver aften er Idasletten rød af blod."*
- A selector for **public** tournaments. This shows all none archived tournaments that have `IsPublic = true`. Each tournament is a clickable card that navigates to its detail page.
- A (deliberately less prominent) link to historical tournaments (shows archived and private tournaments).
 
### `/tournaments` — All tournaments
- Lists all historical tournaments.
- A **Create tournament** button (requires login).
 
### `/tournaments/{tournamentId}` — Tournament detail
**Main area — scoreboard**
- Table of `TournamentPlayer`s showing won, lost, and `Score` (per the selected score system).
- An **Add player** button at the top opens a dialog to add a player to the tournament. Adding a player by initials that haven't been used before also creates a `User`.
 
**Right column (≈ ¼ width)**
- Top: **Create match** button → navigates to `/tournaments/{tournamentId}/create-match`.
- Card: **next 5 planned matches** (if any). Each is clickable and navigates to the create‑match page **pre‑filled** with that match's data.
- Card: **recent 5 played matches** (if any). Each is clickable and navigates to that match's detail page (same as create‑match but read‑only). 
- Below the cards: a **View all matches** link → `/tournaments/{tournamentId}/matches`.
 
### `/tournaments/{tournamentId}/create-match`
- Inputs for the **initials** of each team's players, plus the score.
- **No login required.**
- Match name and team names are **not** input fields (auto‑derived — see model clarifications).
- Unregistered initials are allowed and auto‑create the players (and a user if not already defined).
- Below the initials input: a **Select from list** link that opens a dialog of existing players (checkboxes).
- Suggestion from the original: generate the match `Id` before navigating here so the same page can be reused for editing a planned match.
 
### `/tournaments/{tournamentId}/matches`
Two tables:
- **Planned matches** — with two actions:
  - **Add planned match** — dialog to enter the players' initials for one match.
  - **Plan several matches** — dialog (see fields below).
- **Match results** — completed matches.
 
**"Plan several matches" dialog fields**
- *Plan based on a previous tournament* — optional; shows the seed tournament (selectable if not already set).
- *Number of games per player.* This is used to calculate how many matches should be created.
- *Fixed team* — should teams reshuffle after each match?
- *Seeding type:*
  - **Random** — teams chosen randomly.
  - **Equality** — using the seed tournament, pair best with worst (1+N, 2+(N−1), …).
  - **Fair** — split ranked players into a top half and a bottom half, then pair the best of the top half with the best of the bottom half, and so on. *Example given:* 10 players → 1+6, 2+7, 3+8, 4+9, 5+10.
 
### `/tournaments/create`
Configure: Name, MaxPlayerCount (optional), TeamSize (default 2), PointsToWin (default 5), ScoreSystem (dropdown — consider an info icon explaining each system), IsPublic.
- A **Create** button.
- A **Create and Plan** link below it. **⚠️ CLARIFY:** where does it navigate after creating — `/plan-match`, `/matches`, or `/players`?
 
### `/tournaments/{tournamentId}/players`
- A players table with an **Add a player** button at the top:
  - **Add player** — dialog for initials and an optional name.
- Below the table, an **Add players based on a previous tournament** section:
  - If no seed tournament is set, the section is just a menu button listing all previous tournaments.
  - Once a tournament is selected, it lists that tournament's players ordered by their score there, each with a **+ / −** button. Clicking **+** adds that player to the current tournament and strikes through their name in the list.
 
### `/users/{userId}`
Cross‑tournament stats for a single player.
 
### `/login`
- Azure AD login via an app registration.
- A **second, test‑only login option** shown next to the Microsoft button — see §6 (Testing).

## 5. Multi‑round / seeding flow

A tournament can consist of multiple rounds, each represented as a separate tournament with `ParentTournamentId` linking to the previous round. Players from the parent tournament carry over to the child tournament, but their scores reset. This allows for a flow where players compete in an initial tournament, then the top N players advance to a second tournament (round 2), and so on. The `RoundNumber` field tracks which round a tournament is in.

The seed tournament can be used on a single round tournament or tournament needs multiple rounds.

## 6. Authentication & permissions
 
- Login is **optional** for general use.
- **Login required for:** creating a tournament; editing a match that is already `Done` (which require recalculation of match results)
- **No login required for:** recording a new match result (`/create-match`).
 
**Forwarded headers (Fly.io):** Configure `UseForwardedHeaders` with `KnownNetworks` and `KnownProxies` **cleared**, so ASP.NET Core trusts Fly's proxy and generates `https://` redirect URIs for Azure AD.

## 7. Tech stack & architecture
 
**Stack**
- C#, Entity Framework Core, **SQLite**.
- Razor Pages for rendering.
- **basecoat** UI via CDN (https://basecoatui.com/installation/#install-cdn). Do **not** install Tailwind as it is included in the CDN bundle. Components reference: https://basecoatui.com/kitchen-sink/.
- Flexbox for layout.
- A **light ("white") theme** — not dark.
 
**Local database**
Use **SQLite in‑memory mode** locally (works with migrations + seeding) and a file‑based SQLite database in production. Confirm this interpretation.
 
**Migrations**
- Always create migrations with the `dotnet ef` CLI.
- Apply migrations automatically on app startup. *(Record this rule in `AGENTS.md`.)*
 
**Deployment**
- Deploy to Fly.io using the `fly` CLI.
- Also add a **GitHub Action** that deploys `main` to Fly.io on push.
 
**Projects**
- `Idasletten`
- `Idasletten.Tests`
 
**Architecture — CQRS + vertical slices (MediatR)**
 
Folders inside `Idasletten`:
- **Pages** — Razor pages with minimal logic; they only send commands/queries via MediatR.
- **Features** — one folder per feature/slice, each containing its handlers, commands, queries, entities, etc. Within a slice, commands and queries get their own sub‑folders. Handlers may use `DbContext` directly (avoid repositories/services). **Every command handler publishes an event at the end** (e.g. `CreateUserHandler` → `UserCreated`). 
- **Shared** — anything not specific to one feature.

## 8. Testing
 
- Integration/feature tests use a **custom `WebApplicationFactory`** with an **in‑memory database**.
- The factory **seeds data** both when running tests and when running the app locally.
- **Test data factories:** a static `Any` class in the test project with methods like `Any.User()` that initialise all fields with random values.
- **xUnit**, **AAA** pattern (Arrange / Act / Assert).
- Test method naming: `Should_DoSomething_When_ConditionIsFulfilled`.
- Prefer **simple stubs** over mocking frameworks when a dependency is needed.
- **Test‑user login:** a second login option (next to Microsoft Azure), enabled **only** when both `TestUser__Password` and `TestUser__Email` env vars are set. This user is also seeded into the database.
